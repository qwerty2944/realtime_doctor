# 근거 우선(Evidence-First) 전환 + 청구 누락 탐지 계획

두 가지 외부 사례에서 출발한다.

1. **agentic-first CRM (trycompai/crm)** — 에이전트는 확신 점수를 매기지 못한다.
   사실·증거가 확실하면 기록하고, 애매하면 사람에게 확인만 요청한다.
   판단 기준은 코드가 아니라 마크다운 워크플로 문서에 적는다.
2. **August Health** — 새로운 케어 기능이 아니라 **이미 제공했지만 청구하지 못한 서비스**를
   찾아준다. 의료 판단을 대신하는 AI는 신뢰를 얻는 데 오래 걸리지만, 청구 누락은 효과가
   숫자로 즉시 보인다.
   (주의: 매출 +20% / 사고 −23% 는 표본 수·측정 기간 미공개의 **회사 자체 발표**다.
   우리 자료에 인용하지 않는다. 필요하면 파일럿에서 우리 숫자를 직접 만든다.)

두 사례는 같은 규칙으로 수렴한다: **모델의 자신감이 아니라 검증 가능한 증거를 화면에 올린다.**

---

## 파트 A — 근거 우선 전환

### E1. confidence 퍼센트를 근거로 교체 [최우선]

**현재 상태 (문제)**
- `src/main/prompts.ts` 의 `ANALYSIS_RESPONSE_SCHEMA` 가 감별진단마다 `confidence` 를 요구한다.
- `src/renderer/diagnosis/App.tsx` 가 그것을 High/Medium/Low + 퍼센트 **배지**로 렌더한다
  (`confidenceLabel`).
- `src/shared/types.ts` 의 `DifferentialDiagnosis.confidence` (M3 에서 optional 로 바뀜).

의사는 그 숫자를 임상적 사전확률로 읽는다. 실제로는 모델이 그럴듯하게 보이려고 고른
토큰이다. CRM 에서 부풀려진 확신은 기회 하나를 놓치는 정도지만, 진료에서는 숫자 하나가
감별 순서를 바꾼다. **우리 도메인에서 이 규칙은 CRM 보다 더 강하게 적용돼야 한다.**

**바꿀 것**
- 스키마에서 `confidence` 제거. 대신 `supporting_findings[]` 를 요구한다 —
  각 항목은 `{ finding, source }` 이고 `source` 는 **전사 발화 인덱스 또는 문진 답변 키**다.
  모델이 만들어낸 문장이 아니라 실제로 존재하는 발화를 가리켜야 한다.
- 렌더러: 퍼센트 배지 → 근거 목록. 각 근거를 누르면 전사 창의 해당 발화로 이동.
- **근거를 대지 못하는 진단은 목록에서 내린다.** "확인 필요"(E2)로 보낸다.
- 이미 붙여둔 PubMed 문헌 근거(`src/main/evidence.ts`, M4)와 나란히 놓는다 —
  환자 근거(이 환자에게서 관찰된 것)와 문헌 근거(이 진단이 일반적으로 어떻게 판단되는지)는
  다른 축이므로 시각적으로 구분한다.

**검증 기준**: 감별진단 창의 모든 항목이 클릭 가능한 발화 근거를 최소 1개 갖는다.
근거 없는 항목이 렌더되면 실패.

### E2. questions 창을 "확인 요청 큐"로 재정의

**현재 상태**: M3 에서 확인했듯 questions/terms 창은 대부분 비어 있다. 문진 스키마에
대응 필드가 없어서 `patientQuestions()`/`patientTerms()` 가 빈 배열을 돌려준다.
용도가 "AI 가 추천하는 질문"이라는 막연한 상태다.

**바꿀 것**: 이 창을 **에이전트가 판단을 포기하고 사람에게 넘긴 것**의 큐로 만든다.
- 증상 발생 시점이 모호함 / 복용약 이름이 불분명 / red flag 기준에 걸릴락 말락 함 /
  E1 에서 근거 부족으로 내려온 진단 후보.
- 각 항목은 왜 애매한지(어떤 발화가 모호한지)를 함께 보여준다.
- 의사가 답하면 그 답이 기록에 남고, 해당 항목은 큐에서 사라진다.

용도가 선명해지고 신뢰가 올라간다. 모르는 걸 모른다고 하는 시스템이 아는 척하는
시스템보다 임상에서 오래 쓰인다. 그리고 파트 B 의 청구 항목이 들어올 자리가 여기다.

### E3. 사실과 해석의 분리

**현재 상태**: `intake_results` 가 환자가 **말한 것**(soap_json.transcript, 구조화된 답변)과
AI 가 **결론 내린 것**(differentials_json, SOAP 의 A/P, red_flag)을 한 덩어리로 저장한다.

**바꿀 것**
- 사실(발화·구조화 답변)은 기록으로, 해석(감별진단·red flag·A/P)은 **출처가 붙은 의견**으로
  분리한다. 해석에는 모델명 + 프롬프트 버전 + 생성 시각을 단다.
- 해석은 재생성 가능해야 한다. 모델을 바꿨을 때 과거 기록을 오염시키지 않고 해석만 다시 뽑는다.
- `intake_results.version` 이 이미 있으므로 확장 지점은 있다.

법적으로도 실질적이다. "환자가 뭐라고 했는가"와 "AI 가 뭐라고 판단했는가"가 섞여 있으면
나중에 분리할 수 없다.

### E4. 판단 기준을 마크다운으로 (안전장치 선행)

**현재 상태**: `kiosk/lib/intake/redFlags.ts` 의 `BUILTIN_RED_FLAGS` 7종이 코드 상수다.
M6 에서 "편집 UI 없이 테이블만 만들면 영원히 빈 테이블 = 규칙 없음"이라는 이유로 그렇게 뒀다.

**바꿀 것**: 기준을 마크다운 워크플로 문서로 뺀다. 안과와 정형외과의 red flag 는 달라야 하고,
릴리스 없이 원장이 자기 진료과에 맞게 고칠 수 있어야 한다.

**[HARD] 다만 여기엔 제동이 필요하다.** 의료 판단 기준을 자유 편집 가능한 텍스트로 두는 것은
CRM 의 "이 사람이 그 사람 맞나"와 위험도가 다르다. 최소한 이것들이 함께 가야 한다:
- 변경 이력과 작성자 기록
- 기본값으로 되돌리는 경로
- 기본 규칙 삭제 금지(비활성화만 허용)

안전장치 설계가 끝나기 전에는 착수하지 않는다.

### 가져오지 않을 것

- **도구를 파일 하나씩 쪼개는 구조** — 우리는 에이전트 루프가 아니라 정해진 파이프라인이다.
  그 분할은 LLM 이 도구를 골라야 할 때 유효하다.
- **"DB 는 에이전트의 공책"** — 진료 기록은 공책이 아니라 법적 보존 대상이다.
  에이전트가 임의로 고쳐 쓰면 안 된다. E3 의 분리가 우리 버전의 답이다.

## 파트 B — 청구 누락 탐지

### 왜 이게 제품의 답이 될 수 있는가

월 77,000원을 "AI 가 감별진단을 도와드립니다"로 파는 것은 어렵다. 의사는 자기 진단에
자신이 있고, 의료 판단을 대신하는 AI 는 신뢰를 얻는 데 오래 걸린다.

같은 77,000원을 **"지난달 놓친 청구 N원을 찾았습니다"**로 팔면 계산이 즉시 끝난다.
해지율도 같은 이유로 낮아진다. S1~S5 로 구독 시스템은 다 지었지만,
**왜 돈을 낼 만한가**에 대한 가장 강한 답이 여기 있을 수 있다.

### 우리가 유리한 이유

August Health 는 EMR 의 구조화된 필드를 본다. 우리는 **진료실에서 실제로 오간 대화 전문**을
갖고 있다(`sessions` / `transcript_chunks`). 차트에 안 적힌 것은 EMR 에 흔적이 없지만,
의사가 8분간 생활습관 교육을 했다면 녹취에는 남아 있다.

한국 의원에서 새는 지점은 대체로 "안 한 것"이 아니라 **"하고도 안 적어서 못 받는 것"**이다.

### 이미 있는 자산

`righthand_voice` 에 HIRA 수가·약가 공공데이터를 다루는 코드가 남아 있다
(`app/src/lib/pubdata/`, `test_master` 테이블, `resolveSessionTestFees`,
마이그레이션 0012/0013). Supabase 프로젝트는 지웠지만 코드는 그대로다 —
환자 기능(M1~M6)을 옮겼던 것과 같은 방식으로 이식할 수 있다.

### [HARD] 반드시 지켜야 할 선

**청구 가능성을 "제안"하는 순간 부당청구 방조가 된다.** 심평원 삭감과 현지실사의 법적
책임은 의사가 진다. AI 가 "이것도 청구할 수 있습니다"라고 넉넉하게 권하면 그 조언이
의사를 위험에 빠뜨린다.

규칙은 파트 A 와 동일하다.

- [HARD] **녹취가 증거하는 것만 보여준다.** 추정·권유 금지.
- [HARD] 확신 퍼센트 금지. `"교육상담료 청구 가능(87%)"` 이 아니라
  `"12:04–12:12, 8분간 식이·운동 교육 — 해당 발화: '…'"` 를 보여주고 **판단은 의사가 한다.**
- [HARD] 근거를 못 대면 화면에 올리지 않는다. 애매하면 E2 의 확인 요청 큐로 보낸다.
- [HARD] **탐지만 하고 입력은 의사가 한다.** 청구 소프트웨어와 연동하지 않는다.
  통합 부담과 법적 노출을 동시에 낮춘다.
- [HARD] 화면에 "청구하세요"가 아니라 "이런 행위 기록이 있습니다"로 쓴다. 문구가 곧 책임 경계다.

### 단계

- **B1. 수가 데이터 이식** — righthand_voice 의 pubdata/HIRA 코드를 가져와 수가 마스터를 세운다.
  전체가 아니라 **자주 새는 항목부터** (아래 미결 사항 참조).
- **B2. 탐지 엔진** — 녹취 + 문진 기록에서 "수행된 행위"를 추출한다. 각 후보는 반드시
  발화 인용과 시간 구간을 갖는다. 근거 없는 후보는 만들지 않는다.
- **B3. 표시** — E2 의 확인 요청 큐에 얹는다. 진료 종료 시 "이번 진료에서 기록된 행위" 목록.
- **B4. 리포트** — 월 단위로 "탐지된 미기재 행위 N건". 파일럿 의원에서 **우리 숫자**를 만든다.
  남의 마케팅 숫자보다 강하다.

### 미결 — 도메인 지식 필요

이 부분은 진료 현장 지식이라 혼자 설계하면 안 된다. 착수 전에 확인이 필요하다.

- 실제로 어느 항목이 자주 새는가? (교육상담료 / 만성질환관리 / 심층진찰 / 처치·시술 …)
- 대상 진료과는? 수가 체계와 새는 항목이 과마다 다르다.
- 청구 실무를 누가 하는가? 원장 본인 / 원무과 / 청구 대행 — 화면을 누가 보는지가 달라진다.
- 삭감 위험이 큰 항목은 아예 제외해야 하는가?

## 순서

1. **E1** (confidence → 근거) — 범위가 작고 이미 만든 PubMed 근거를 활용한다. 즉시 착수 가능.
2. **E2** (questions 창 재정의) — B3 가 들어올 자리를 미리 만든다.
3. **E3** (사실/해석 분리) — 스키마가 걸려 중간 규모.
4. **B1~B4** — 도메인 지식 확인 후.
5. **E4** (마크다운 워크플로) — 안전장치 설계 후. 가장 마지막.
